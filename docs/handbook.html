How CampusOne holds a college together

CampusOne is the backend for a multi-tenant college-management SaaS — one API, any number of colleges, each seeing only its own students, faculty, and ledgers. This handbook is the map: how a request finds its tenant, how a role becomes a permission, and how the five flows that matter most actually move through the system.

01

Architecture

Every college that signs up is a tenant. There's one Postgres database and one schema — not one database per college — so isolation has to be enforced by the database itself, not just remembered in application code. That's the single decision everything else in this handbook traces back to.

Tenants & Row-Level Security

Every table carries a tenantId column, and Postgres Row-Level Security is the last line of defense — not an optional extra. A request's JWT resolves to a tenant, that tenant id is carried through the request via AsyncLocalStorage, and a Prisma client extension sets app.current_tenant before every single query, inside the same transaction as the query itself. A query that somehow runs with no tenant context set doesn't silently see everything — it throws.

Roles, permissions, and modules

Roles aren't a hardcoded enum — Role, Permission, and RolePermission are ordinary database rows, seeded per tenant. A route never checks "is this user a HOD" — it checks "does this role hold STUDENT_READ," which means the grants underneath a role name can change without touching a single line of route code. Ten system roles ship by default, from the cross-tenant PLATFORM_ADMIN down to STUDENT and PARENT.

Orthogonal to roles: modules. CORE is always on; everything else — ACADEMICS, FINANCE, HOSTEL_TRANSPORT, and so on — is a row in TenantModule a college can be sold, or not. A route checks both: the module gate first, then the permission.

Getting started

Five steps stand between a fresh clone and your first authenticated call.

  1. Bring up Postgres, Redis, and the schema

    Docker Compose creates the non-superuser campusone_app role RLS actually depends on.

    docker compose up -d
npm install
npm run prisma:migrate   # applies the schema + RLS policies
npm run prisma:seed      # permission catalogue + demo tenant/admin
npm run dev

  2. Log in as the seeded demo admin

    Every tenant needs a resolvable email — that's why login looks a user up by email before it knows the tenant.

    curl -X POST http://localhost:4000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@demo-college.test","password":"Passw0rd!"}'

# 200 →
{ "user": { "role": "SUPER_ADMIN", "mfaEnabled": false, ... }, "token": "eyJhbGci..." }

  3. Call an endpoint with the token

    Every list route returns the same envelope, so pagination works identically everywhere.

    curl http://localhost:4000/api/v1/departments \
  -H "Authorization: Bearer $TOKEN"

# 200 →
{ "data": [ { "name": "Computer Science", "code": "CSE", ... } ],
  "meta": { "page": 1, "pageSize": 10, "total": 4, "totalPages": 1 } }

  4. Read an error the same way everywhere

    One shape for every non-2xx response — a machine code to branch on, a message to show.

    curl -X POST http://localhost:4000/api/v1/departments \
  -H "Authorization: Bearer $TOKEN" -d '{"name":"CSE"}'

# 409 →
{ "message": "Department code \"CSE\" is already in use.", "code": "DUPLICATE_CODE" }

  5. Browse the rest interactively

    Everything past this point — all 38 modules — is documented request-by-request in Swagger.

    open http://localhost:4000/api/docs
03

Auth & MFA

Access is a short-lived JWT; refresh is an opaque token in an httpOnly cookie, stored only as a SHA-256 hash, rotating on every use. MFA is TOTP (RFC 6238) — when it's on, a missing or wrong code fails the same POST /login call before any token is issued, rather than a separate challenge step. 

sequenceDiagram
  participant C as Client
  participant A as POST /auth/login
  participant DB as Postgres

  C->>A: email + password
  A->>DB: find user by email (bootstrap — tenant not known yet)
  DB-->>A: user row + tenantId
  A->>A: bcrypt.compare(password, hash)
  alt wrong password, 5th time
    A-->>C: 429 — account locked 30s
  else MFA enabled, no code yet
    A-->>C: 401 MFA_REQUIRED
    C->>A: same call again, + mfaCode
    A->>A: verify TOTP (±1 step) or a recovery code
  end
  A->>DB: create RefreshToken (hash only)
  A-->>C: 200 user + access token,
Set-Cookie refreshToken (httpOnly)
API keys work differently on purpose. An X-API-Key header authenticates as the user who created it — same tenant, same role, same permission checks — rather than carrying its own separate scope system. One less authorization model to keep in sync.
Forgot password, honestly. POST /auth/forgot-password never reveals whether an email matched an account, and issues a single-use, 30-minute PasswordResetToken when it does. Nothing in this codebase can actually send that email yet — the attempt is recorded FAILED, same as every other notification channel — so the response also returns the raw token directly, but only outside production. Both reset-password and change-password revoke every other active session for the user.

Using the API by role

Every route is gated by a permission, and every permission maps to a set of roles — but that mapping is data (Role/RolePermission rows, see §1), not a hardcoded switch statement. What follows is what the default seed grants each of the ten system roles today; a tenant's actual grants can diverge if an admin edits them via POST /users/:id/role and the RBAC tables.

COLLEGE_ADMIN		 The college's own IT/ops owner. Everything. Every permission key, unconditionally — including Billing, API Keys, Webhooks, Integrations, and RBAC itself. Nothing, within their own tenant. (PLATFORM_ADMIN is the one cross-tenant role above these — not tenant-created, seeded globally.)
DEPARTMENT_ADMIN
HOD		 Runs a department day-to-day. Full CRUD on the academic structure, all of Academic Management and College Operations, approvals, class groups for any section. Effectively "everything except platform-tier." Billing, API Keys, Webhooks, Integrations — deliberately kept to SUPER_ADMIN/COLLEGE_ADMIN. Not code-restricted to their own department either — the grant is tenant-wide, same as every role here.
EXAM_ADMIN Runs the examination cycle. Create/manage exams and schedules, verify/publish/revise marks, read reports. Can't enter marks (that's MARKS_ENTER, a Faculty grant) — only verify/publish what's already entered.
FACULTY Teaches; owns a login provisioned at creation. Mark/edit attendance, approve leave, manage & grade assignments, enter marks, post announcements & verify documents, log any student's activity, post in class groups for sections they teach. Read-only on the academic structure itself (can't create a Program or Section) — and can't verify/publish marks, only enter them.

The self-service pattern, worked through

A student calling GET /attendance/student/:studentId doesn't know their own Student.id — they only have their login. Routes built for self-service come in two shapes, and it matters which one a given route is — Swagger states it per-route, but the shapes are: a dedicated /mine route that takes no id at all, or a create/query route where the id is an optional field (body or query) — pass one and staff can act on someone's behalf; omit it and it resolves the caller's own linked profile instead. A handful of staff-oriented reads (/attendance/student/:studentId, /leave/balance/:studentId) take a required path id with no self-resolution at all — a student holds the read permission for these in principle, but has no route to look up their own Student.id to call them, so treat those two as staff/faculty tools today, not student self-service. 

# Dedicated self-service routes — no id, ever
curl http://localhost:4000/api/v1/fees/invoices/mine \
  -H "Authorization: Bearer $STUDENT_TOKEN"

# Optional query param — omitted, resolves to the caller's own Student row
curl http://localhost:4000/api/v1/examinations/results/cgpa \
  -H "Authorization: Bearer $STUDENT_TOKEN"
# staff/faculty pass ?studentId=... on the same route to check anyone's

# Optional body field — a student requesting their own leave
curl -X POST http://localhost:4000/api/v1/leave/requests \
  -H "Authorization: Bearer $STUDENT_TOKEN" \
  -d '{"leaveTypeId":"lt_1","startDate":"2026-03-10","endDate":"2026-03-12","reason":"Family event"}'

# Same route, staff filing it FOR a student — one extra field, nothing else changes
curl -X POST http://localhost:4000/api/v1/leave/requests \
  -H "Authorization: Bearer $STAFF_TOKEN" \
  -d '{"leaveTypeId":"lt_1","startDate":"2026-03-10","endDate":"2026-03-12","reason":"Family event","studentId":"stu_9f2a"}'

# Staff recording a fee payment against an invoice
curl -X POST http://localhost:4000/api/v1/fees/invoices/inv_7c1/payments \
  -H "Authorization: Bearer $STAFF_TOKEN" \
  -d '{"amount":15000,"method":"CASH"}'

# Admin: provision a department, then hand a user the HOD role
curl -X POST http://localhost:4000/api/v1/departments \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -d '{"name":"Computer Science","code":"CSE","status":"ACTIVE"}'
curl -X POST http://localhost:4000/api/v1/users/usr_4b1/role \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -d '{"roleName":"HOD"}'

Building an admin panel

Everything above is the machinery; this is what it means for the app you're actually building. Almost every screen in a CampusOne admin panel is one of two shapes — a session wrapper you build once, and a CRUD list/detail screen you build roughly thirty times with the same four calls.

1. The session wrapper (build this once)

Log in, keep the access token in memory (a store/context — not localStorage, since a JWT sitting there is readable by any script that gets injected onto the page). The refresh token never touches your JS at all — it's an httpOnly cookie the browser manages for you.

  1. On every request, attach the token

    Authorization: Bearer <token>. Also set credentials: 'include' (fetch) or withCredentials: true (axios) on every call — without it the browser won't send the refresh cookie cross-origin, and /auth/refresh will silently 401 forever.

  2. On a 401 from any call, try one silent refresh

    Call POST /auth/refresh (no body — the cookie does the work), swap in the new token, retry the original request once. If the refresh itself 401s, the session is actually over — clear state and send the user to /login. Don't retry a second time; a refresh token is single-use and rotates, so a loop here just burns tokens.

  3. On app load, restore the session

    You have no token in memory yet (e.g. after a page reload), and /auth/me requires one — so call POST /auth/refresh first. A 200 means the httpOnly cookie was still good; store the new token, then call GET /auth/me to get the user. A 401 from the refresh call means there's no session to restore — go straight to /login.

  4. Build a can(permissionKey) helper

    Fetch GET /roles once per session and find the entry matching me.role — its permissions array is everything the current user can do. Use it to hide/disable buttons for actions they don't have. This is a UX nicety only; the API enforces the real boundary regardless of what the UI shows, so a hidden "Delete" button is not a substitute for the server's own 403.

2. The CRUD screen (build this ~30 times)

Every entity module — Departments, Students, Faculty, Programs, Fee Structures, Books, Vehicles, and on — follows the same four-call shape. Learn it once on Departments and every other list screen in the panel is the same component with different field names, which Swagger gives you exactly (schema, required fields, enums) per module.

Screen actionCallNotes
List (with search, pagination, filters)GET /Query params vary by module (search, status, foreign-key filters) — render meta.totalPages for pagination controls.
Row detail / edit form prefillGET /:idNot every module has this as a separate call — some list responses already carry everything a row needs.
CreatePOST /Body is the module's *Input type. A 422 means render Zod's per-field messages next to the form fields, not a toast.
EditPUT /:idSame body shape as create, almost always.
DeleteDELETE /:idA 409 here is expected, common UX — it means the row is referenced elsewhere (e.g. DEPARTMENT_IN_USE). Show the reason, don't treat it as a bug.

3. Module-gated navigation — a real gap, not an oversight

There is currently no endpoint that lists which modules a tenant has enabled — see the Platform admin console note in CLAUDE.md; that whole console (tenant list, module enable/disable, plan management) isn't built yet. GET /institution returns the tenant row, not its module list. Until that exists, an admin panel has two honest options: hardcode the nav to match known plan tiers and let a disabled module 403 if the tenant doesn't actually have it, or attempt the first call for a section lazily and catch the 403 — its message names the missing module ("... ACADEMICS ..." etc.) so you can render "not on your plan" instead of a generic error. Neither is great; both are what's actually available today.

5. Worked example: the Departments screen, end to end

This is the whole pattern from §2, with real field names, so you can copy the shape directly. 

// List — render the table + pagination controls
const res = await fetch(`/api/v1/departments?page=${page}&search=${q}`, {
  headers: { Authorization: `Bearer ${token}` }, credentials: 'include',
})
const { data, meta } = await res.json()
// data: Department[], meta: { page, pageSize, total, totalPages }

// Create — submit the form
const created = await fetch('/api/v1/departments', {
  method: 'POST', credentials: 'include',
  headers: { Authorization: `Bearer ${token}`, 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Computer Science', code: 'CSE', status: 'ACTIVE' }),
})
if (created.status === 422) {
  const { details } = await created.json()  // { code: ["Code is required"] } — map onto form fields
}
if (created.status === 409) {
  const { message } = await created.json()  // "Department code \"CSE\" is already in use." — show inline
}

// Delete — confirm, then handle the "in use" guard
const deleted = await fetch(`/api/v1/departments/${id}`, {
  method: 'DELETE', credentials: 'include', headers: { Authorization: `Bearer ${token}` },
})
if (deleted.status === 409) {
  const { message } = await deleted.json()  // "... still has students" — surface it, don't retry
}

Core flows

Five flows that show the shape of the rest: a lifecycle that ends in a new row elsewhere in the system, a ledger that recomputes itself, a state machine that refuses direct edits once locked, and two ways data leaves the system — to a user's own notification list, and to a URL the tenant supplied.

Admissions → enrollment

An application steps forward one stage at a time through /advance. ENROLLED is reachable only through its own endpoint — the one action that actually creates a Student row, through the exact same path a manual entry uses. 

flowchart LR
  APPLIED --> DV["DOCUMENT_VERIFICATION"] --> SL["SHORTLISTED"] --> AP["APPROVED"] --> OF["OFFERED"] --> AC["ACCEPTED"]
  AC -->|"POST /:id/enroll"| EN["ENROLLED
+ Student row created"]
  APPLIED -.->|"reject / withdraw, any stage"| RJ["REJECTED / WITHDRAWN"]

Attendance: lock, then only correct

The roadmap's own flagship example of "not just CRUD." Once a session is LOCKED, a record can never be edited directly again — only challenged with a correction request, which an approval turns into an audited before/after change. 

flowchart LR
  DR["DRAFT
mark records"] -->|"submit"| SB["SUBMITTED"]
  SB -->|"lock"| LK["LOCKED"]
  LK -->|"POST /records/:id/correction"| PD["Correction: PENDING"]
  PD -->|"approve"| UP["Record updated +
before/after audit entry"]
  PD -->|"reject"| LK

Fees: a recomputed ledger, not a stored balance

An invoice's status is never trusted as stored truth — it's recomputed from every payment and adjustment on every write, the same way SGPA/CGPA are computed on read elsewhere. A waiver is the one sticky manual override the recompute leaves alone.

  INV["FeeInvoice"] --> ADJ["Adjustments:
DISCOUNT · SCHOLARSHIP · FINE"]
  INV --> PAY["Payments recorded"]
  ADJ --> CALC{"recompute payable
vs. net paid"}
  PAY --> CALC
  CALC -->|"netPaid ≥ payable"| PD["PAID"]
  CALC -->|"0 < netPaid < payable"| PT["PARTIAL"]
  CALC -->|"netPaid = 0, past due"| OD["OVERDUE"]
  CALC -->|"netPaid = 0"| PN["PENDING"]

recompute skips it"| WD["WAIVED"]

Notifications: one real channel, two honest stubs

Three things fire a notification: an announcement going live, a class-group message, and a BullMQ job that scans every tenant every 15 minutes for announcements about to expire. IN_APP is always real. EMAIL, SMS, and PUSH only even attempt a delivery if the tenant has switched the matching integration on — and even then, nothing actually sends; the delivery is logged FAILED with the reason why, rather than pretending to succeed. 

flowchart LR
  E1["Announcement published"] --> D["dispatchNotification()"]
  E2["Class group message"] --> D
  E3["BullMQ: expiry scan,
every 15 min"] --> D
  D --> IA["Notification row created
= IN_APP delivered"]
  D --> CK{"EMAIL / SMS / PUSH
enabled for this tenant?"}
  CK -->|"no"| SK["No delivery row"]
  CK -->|"yes"| FL["NotificationDelivery: FAILED
— config-only, reason recorded"]

Webhooks: signed, and checked twice

A tenant-supplied URL that this server POSTs to is a real SSRF vector, not a hypothetical one — so it's checked against ssrfGuard both when it's registered and again immediately before every delivery, which is what actually defends against DNS being rebound to a private address in between. 

sequenceDiagram
  participant S as CampusOne
  participant G as ssrfGuard
  participant T as Tenant's URL

  S->>G: assertPublicHttpsUrl() at registration
  Note over S: later — an event fires
(student.created, fee.invoice.paid, ...)
  S->>G: assertPublicHttpsUrl() again — DNS may have changed
  G-->>S: still public, still https
  S->>T: POST { event, data }
X-Webhook-Signature: HMAC-SHA256
  T-->>S: 2xx or error
  S->>S: WebhookDelivery row: DELIVERED or FAILED

Conventions & errors

Every list looks the same

{
  "data": [ ],
  "meta": {
    "page": 1, "pageSize": 10,
    "total": 42, "totalPages": 5
  }
}

Every error looks the same

{
  "message": "Human-readable",
  "code": "DUPLICATE_CODE",
  "details": { }
}

Status codes in practice

CodeMeaning here
401Bad credentials, expired session, or — distinctly — MFA_REQUIRED / MFA_INVALID.
403A module name in the message means the tenant hasn't enabled it; otherwise it's a permission gap.
409A domain conflict — DUPLICATE_CODE, ALREADY_PAID, ROOM_FULL, and so on, one per module.
422VALIDATION_ERROR — Zod rejected the body before it reached any business logic. details is a field → messages map.
429Rate limit — tighter on /auth/login and /auth/refresh specifically.
